FastVideo 把减少生成步数、降低每步计算量和优化硬件执行放进同一套训练与推理框架。这对视频生成尤其有价值：视频既有较长的 token 序列，又需要反复去噪；对图像生成和编辑，也有可以复用的技术，但必须逐模型确认支持范围。

本文基于项目提交 [`c938a8aa2b856a594f791a61875ba0bdac5ef318`](https://github.com/hao-ai-lab/FastVideo/tree/c938a8aa2b856a594f791a61875ba0bdac5ef318)，整理 README、架构、蒸馏、注意力、模型支持矩阵和应用文档。**性能与兼容性数字为项目文档报告，本文没有进行 GPU 性能实测；场景选择与落地顺序是基于这些资料的分析建议。**后续版本可能改变接口、支持范围与默认设置。

## 先看问题：为什么视觉生成这么贵

典型的扩散或流匹配生成流程是：

```text
文字、参考图 → 条件编码
                    ↓
初始噪声 → 多次 DiT 前向 → 图像／视频 latent → VAE 解码 → 图片或视频
```

成本主要来自两个方面：大模型要反复运行，且每次运行处理的序列很长。粗略地写：

$$
T_{\text{生成}} \approx T_{\text{编码}} + N_{\text{前向}}\,T_{\text{每次前向}} + T_{\text{解码与输出}}.
$$

这只是单个生成请求的计算分解；线上还要考虑排队、输入上传、安全检查和传输。

对于全局注意力，注意力计算量约为 $O(N^2d)$。在压缩率和 patch 大小不变时，帧数翻倍意味着 token 数近似翻倍，注意力计算可能接近四倍；整个模型还包括线性层、FFN 等部分，因此不能把这个倍率直接套到端到端耗时。

FastVideo 的技术可以按三个方向理解：**少运行几次、每次少算一些、让剩下的计算更高效。**

| 技术 | 主要优化对象 | 权重或训练要求 | 需要关注的代价 |
| --- | --- | --- | --- |
| DMD／DMD2 少步蒸馏 | DiT 前向次数 | 需要对应蒸馏权重 | 细节、指令遵循和任务覆盖变化 |
| VSA 稀疏注意力 | 每步注意力计算 | 主推路线包含训练适配 | 重要远距离关系被遗漏的风险 |
| FlashAttention 等算子 | 访存和执行效率 | 通常无需重训 | 硬件、形状及数值差异 |
| FP8／FP4 与量化感知训练 | 参数存储和计算 | 取决于具体量化方案 | 误差积累与内核兼容性 |
| 缓存与编译 | 重复计算、执行开销 | 需架构和实现支持 | 显存、失效规则与冷启动 |
| 序列并行 | 多 GPU 分摊长序列 | 通常无需重训 | 通信和 GPU 总成本 |

## 少步蒸馏：让学生用更少计算完成生成

普通生成模型可能需要几十次去噪前向；项目发布的部分 FastWan 权重使用三步生成。这需要专门的蒸馏训练，不能仅将普通模型的采样步数调到三步，就期待同样的结果。

DMD2 可以从三个模型角色理解：教师提供目标分布的信息，学生负责少步生成，学习学生分布的 score／critic 模型参与构造分布匹配信号。这里的 critic 不应简单理解成判断视频好坏的二分类器。

它关注的是生成分布的匹配，而非要求每个学生输出逐像素复制同一 seed 的教师输出。模型参数量也不一定显著缩小，主要收益来自**前向次数下降**。

### 哪些产品更适合少步模型

交互预览、批量创意探索、短视频素材生产，往往愿意用少量质量损失换取更快反馈。但商品 Logo、画面文字、复杂结构、多主体关系和稀有风格，应单独建立验收集。

一个合理的产品设计是：用快速模型探索构图与动作方向，筛选后再进入高质量生成或精修。两条路径可能产生不同细节，不能承诺高质量结果只是预览图的无变化增强。

### 训练投入不能忽略

项目蒸馏指南中的部分配方使用 64 张 H200，并包含多小时到数十小时的训练。它们是特定实验配方，不代表所有蒸馏都必须使用同样资源，但足以说明：**部署已有学生权重与自己完成蒸馏，是两个投入不同的项目。**

## VSA：让每一步关注重要的区域

密集注意力让每个 token 与全部 token 交互。Video Sparse Attention（VSA）把序列组织为块，通过块级选择保留重要的 top-k 块，再进行注意力计算。

直观地说，一段花瓣摆动的视频，并不需要每层、每步都对所有背景位置进行相同强度的计算；但花瓣、手部、遮挡物之间的关键关系也可能跨越较远的空间和时间，因此不能仅保留固定小邻域。

稀疏策略既要减少无用计算，也要保住有用关系。块级组织还能让计算更适合 GPU 内核，避免只减少理论运算量、却被索引与访存开销抵消。

### Sparse-distill：少步与稀疏一起适配

FastVideo 的重点路线是把 DMD 和 VSA 联合到训练过程，让学生同时适应少步生成与稀疏注意力。

两种优化作用不同：少步减少前向次数，稀疏降低每次前向的部分成本，因此有叠加空间。但不能直接把两个局部加速倍率相乘当成整站服务收益。

尤其要注意：

- 80% 注意力稀疏率，不等于整个模型快五倍；FFN、投影、块选择、布局转换与解码仍有成本。
- 不应假设任意原始模型切换 backend 后都能无损稀疏化，应选匹配权重或验证训练适配。
- 空间局部纹理容易保留，不代表多人互动、长距离物体运动和小字同样安全。

### STA 与 VSA 的版本关系

项目早期的重要工作包括 Sliding Tile Attention（STA）。本次核对版本中，完整 STA 推理接入已归档至 `sta_do_not_delete` 分支，当前主线重点是 VSA，部分底层 STA 内核仍被保留。学习旧论文与部署当前代码，应分开查阅。

## 量化、编译与并行：把剩下的计算做好

### 权重量化不等于注意力量化

权重量化主要作用于参数存储和线性层；注意力量化作用于 Q/K/V 等注意力计算。一个模型使用 INT4 权重，并不意味着整条流水线都以 INT4 执行。

量化感知训练或蒸馏，让模型在训练中适应低精度误差。项目文档明确提示，对未经过相应训练的权重直接启用部分 FP4 注意力路径，可能损害质量。

硬件也决定是否真正加速：不支持目标低精度计算的设备可能走反量化路径。判断时应确认实际内核、执行精度、显存与端到端时间，不能只看配置名称。

### 编译适合形状稳定的持续服务

`torch.compile` 可以减少执行开销、优化算子组合，但存在图构建和预热成本，输入形状变化还可能触发新编译。常驻、固定分辨率的服务更容易摊薄这部分成本。

项目报告了一个 Wan2.1-T2V-1.3B 案例：A100-80GB、480×832、81 帧、50 步时，端到端从 259.7 秒下降到 198.1 秒。这是特定配置的结果，不是所有模型的收益保证。

性能报告应同时给出冷启动与预热后的稳定耗时，不能只提供其中一项。

### 多卡更快不一定更便宜

序列并行将长序列分给多张 GPU，有助于缓解单卡显存压力、降低延迟，但也带来通信。低延迟在线服务与离线高吞吐服务，最优并行配置可能不同。

评估时同时看请求耗时、吞吐与 GPU 秒数；不要只报告多卡比单卡快多少。

## 图文应用：商品图、海报与图像编辑

这里的“图文”指文生图、图像编辑和多参考图生成。FastVideo 主要服务视觉生成，不是通用图文理解或 OCR 框架。

当前支持矩阵列有 FLUX、SD3.5 和 Qwen-Image-2.1 等模型，但支持加载模型，不代表它支持框架内全部训练、量化、并行和服务能力。

### 商品图与海报：以可交付率评估加速

```text
商品参考图 + 风格描述 → 快速候选 → 人工或规则筛选 → 高质量生成／精修
```

快速模型适合探索背景、构图、配色与光照。正式交付还必须检查商品轮廓、材质、Logo、数字、多图主体一致性与透明边缘。

海报中一个很小的价格或 Logo 可能决定整张图能否使用，因此平均画面质量不足以代表业务质量。稀疏与低精度方案应单独测试这些局部区域。

### 图像编辑：优先复用不变的条件

Qwen-Image-2.1 的 FastVideo 接入支持 Prefix KV Cache，复用文字与参考图 token 的计算，避免每个去噪步骤都重新计算这些条件。这与近似复用正在变化的去噪特征，是不同的缓存策略。

是否可以复用，取决于模型注意力结构和条件依赖。提示词、参考图、位置或其他相关条件变化时，必须按正确规则失效；不能仅凭输入图片相同，就默认所有中间结果都能跨请求命中。

缓存还需要在显存驻留与 CPU 传输之间取舍。缓存命中率高，但传输开销也高，不一定降低总延迟。

### Qwen-Image-2.1 的已接入范围

本次核对文档支持文生图、指令编辑、最多十张有序参考图及 RGBA PNG 输出。支持范围明确限定为**单 GPU、batch 1、未量化推理**；SP/TP、LoRA、提示词改写和 HTTP serving 不在该接入范围。

文档记录了特定 GB200 环境中的数值一致性和显存测量，不应据此推导所有消费卡都已验证。它也说明掩码作为参考图由提示词解释，不能保证掩码外像素严格不变。

这些边界很关键：有 Python 生成接口，与具备成熟的线上图片编辑服务，是不同层级的能力。

### 图片场景的优化顺序

对单张中低分辨率图片，注意力未必是最大瓶颈。建议先测出各阶段占比，再依次评估可靠的注意力算子与编译、架构允许的缓存、已有少步权重，最后考虑稀疏与低精度组合。

高分辨率、多参考图任务的序列更长，稀疏注意力的潜在收益更大，但也需要重新验证空间关系和编辑精度。

## 视频应用：离线生产与实时交互

| 场景 | 可评估的技术 | 质量重点 |
| --- | --- | --- |
| 文生视频、创意预览 | 少步蒸馏、VSA | 动作合理性、提示词遵循 |
| 商品图转视频 | I2V 与匹配的蒸馏权重 | 商品形变、Logo 和身份漂移 |
| 视频编辑、换风格 | 专用编辑模型及适配的加速路径 | 未编辑区域与时间一致性 |
| 实时交互 | 因果／分块生成、历史缓存、流式输出 | 首块延迟、持续速度、控制响应 |
| 音视频联合生成 | 对应的联合模型与蒸馏方案 | 事件声音、口型和时间同步 |

### 离线短视频：两种核心优化都有发挥空间

长序列与多步去噪，使视频天然适合少步和稀疏联合优化。但图生视频不能只检查首帧和末帧：商品结构、文字、手部接触与遮挡可能在中间帧失真。

文生视频蒸馏成功，也不自动证明图生视频同样成功。参考条件需要在相应训练与验证中得到覆盖。

### 实时生成：生成速度与交互能力分开看

双向视频扩散通常让整段视频共同参与去噪。即使生成一整段视频很快，也不天然支持中途改变控制、连续输出。

因果或分块生成让后面的片段依赖先前生成的内容，更适合流式输出和历史缓存。FastVideo 包含 Self-Forcing 等相关训练路径：让模型在训练时面对自己生成的历史，缓解训练与推理条件差异造成的误差累积。

项目的 Dreamverse 提供实时生成与编辑应用，但不同配置的续接机制不一样。例如 FastH3 配置文档描述用上一段末帧作为下一段首帧条件，这不能直接等同于保留完整历史 KV 的因果生成。

实时系统至少要分别测：

1. 请求提交到首个可播放片段的时间。
2. 稳态生成速度是否跟得上播放速度。
3. 控制输入到可见画面变化的延迟。
4. 长时间续接后的漂移、接缝、重复与运动连续性。

播放文件的标称 FPS、生成吞吐 FPS 和交互响应时间，不能混用。

## 读懂性能数字：去噪快不等于接口同比例变快

项目蒸馏指南报告，部分特定模型与分辨率的去噪循环达到 50×、60× 或 90× 加速。这些数字应连同模型、硬件、分辨率、帧数、精度、步数与基线阅读。

举一个计算示例，假设原请求去噪 90 秒、其他阶段 10 秒。即使去噪快了 50 倍：

$$
T_{\text{新}} = 90/50 + 10 = 11.8\text{ 秒},\qquad
S_{\text{整体}} = 100/11.8 \approx 8.5.
$$

这是演示瓶颈转移的算术示例，不是 FastVideo 实测。随着去噪变快，文本编码、参考图处理、VAE、存储和传输会变得更显眼。

同样，固定输入下的低延迟，不代表在线高并发下的 P95 延迟；多 GPU 降低单请求时间，也不代表 GPU 总成本下降。

更贴近内容业务的指标是：

$$
\text{每个合格成品成本}
= \frac{\text{总生成与重试成本}}{\text{最终可用成品数量}}.
$$

如果快速模型让重试和审核明显增加，单次推理便宜并不一定转化为交付便宜。

## 怎样做一次有结论的业务评估

建议将图像编辑与视频生成分成两条评估线，先使用已有匹配权重，再决定是否投入自行蒸馏。每轮尽量只引入一个变化。

| 阶段 | 对比内容 | 需要记录 |
| --- | --- | --- |
| 建立基线 | 原模型、原精度、原采样方案 | 各阶段耗时、显存、质量 |
| 执行优化 | 注意力算子、编译 | 冷／热启动、数值差异 |
| 重复计算优化 | 有条件的 KV 或其他缓存 | 命中、失效、显存与传输 |
| 模型加速 | 匹配的少步、稀疏或量化权重 | 业务可用率、失败类型 |
| 服务评估 | 并发、并行、队列与输出 | P50/P95、吞吐、GPU 秒、重试 |

商品图验收覆盖文字、Logo、颜色、细节与透明边缘；视频验收覆盖身份、形变、物理运动、时间连续性和音画同步。改变模型后，应在同一业务分布上比较质量，不以同一 seed 的逐像素差异代替质量判断。

FastVideo 框架采用 Apache-2.0 许可，但框架许可不自动覆盖模型权重、数据与第三方内核。选型时应逐项检查实际使用的模型和组件许可。
